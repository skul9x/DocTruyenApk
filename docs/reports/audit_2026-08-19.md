## 🔴 Critical Issues (Phải sửa ngay — Ảnh hưởng trực tiếp đến UX)

### 🔴 C1. Network Response Body bị đọc 2 lần — Tốn RAM & CPU vô ích

**File:** [`ApiService.kt`](file:///c:/Users/Administrator/Downloads/DocTruyenApk-main/app/src/main/java/com/skul9x/doctruyen/network/ApiService.kt#L127)

**Triệu chứng:** Trong interceptor của OkHttp, mỗi response API đều bị `peekBody(Long.MAX_VALUE)` — tức là toàn bộ body response (có thể vài MB nếu truyện dài) bị **copy vào RAM thêm 1 lần nữa** chỉ để ghi log.

```kotlin
// Dòng 127 — SỰ CỐ:
val responseBody = response.peekBody(Long.MAX_VALUE).string()
```

**Hậu quả nếu không sửa:**
- Mỗi API call tốn gấp đôi RAM cho response body
- Nội dung truyện dài (100KB+) sẽ bị duplicate hoàn toàn trong memory
- `Long.MAX_VALUE` không giới hạn kích thước → rủi ro OutOfMemoryError trên thiết bị RAM thấp
- Kết hợp với `HttpLoggingInterceptor.Level.BODY` (dòng 93-94) → body bị log **3 lần** (peekBody + logging interceptor + Gson parser)

**Cách sửa:**
1. Chuyển `HttpLoggingInterceptor.Level.BODY` → `.HEADERS` cho production
2. Giới hạn `peekBody(1024)` hoặc chỉ log trong debug build
3. Tốt nhất: Xóa hẳn `peekBody` trong production, chỉ giữ cho debug

### 🔴 C2. ONNX CacheTensor không được giải phóng chủ động — Memory Leak tiềm ẩn

**File:** [`VieNeuOnnxEngine.kt`](file:///c:/Users/Administrator/Downloads/DocTruyenApk-main/app/src/main/java/com/skul9x/doctruyen/tts/vieneu/VieNeuOnnxEngine.kt#L116-L189)

**Triệu chứng:** Trong vòng lặp autoregressive (dòng 124-189), mỗi decode step tạo ra `pastK` và `pastV` mới (danh sách `CacheTensor`), nhưng **danh sách cũ bị thay thế mà không clear reference**. Đặc biệt nghiêm trọng vì:

```kotlin
// Dòng 178-187: Mỗi step tạo list mới, list cũ chỉ chờ GC
val newKList = ArrayList<CacheTensor>(L)  // 12 tensors mới
val newVList = ArrayList<CacheTensor>(L)  // 12 tensors mới
// pastK, pastV cũ bị mất reference nhưng GC có thể không kịp thu
pastK = newKList
pastV = newVList
```

**Hậu quả nếu không sửa:**
- Mỗi chunk inference với 600 max frames tạo ~600 × 24 CacheTensors chờ GC
- Mỗi CacheTensor chứa FloatArray lớn (shape `[1, numHeads, seqLen, headDim]`)
- Với seqLen tăng dần theo mỗi step, memory footprint tăng nhanh → GC pressure cực lớn
- Trên thiết bị 3GB RAM → GC stall gây jitter/giật âm thanh

**Cách sửa:**
- Thêm cơ chế clear/reuse buffer cho CacheTensor (object pool pattern)
- Hoặc: Sử dụng mảng cố định thay vì tạo ArrayList mới mỗi step
- Gọi `System.gc()` hint sau mỗi N frames (tùy chọn, ít hiệu quả)

### 🔴 C3. `topKSample` Full Sort O(V log V) thay vì Partial Sort O(V + K log K)

**File:** [`VieNeuOnnxEngine.kt`](file:///c:/Users/Administrator/Downloads/DocTruyenApk-main/app/src/main/java/com/skul9x/doctruyen/tts/vieneu/VieNeuOnnxEngine.kt#L388-L392)

**Triệu chứng:** Hàm `topKSample` tạo Array mới kích thước V=1024, rồi **sort toàn bộ** chỉ để lấy top 25:

```kotlin
// Dòng 388-392:
val indexed = Array(V) { i -> IndexedLogit(i, workingLogits[i]) }  // 1024 object allocations
indexed.sortByDescending { it.logit }  // Full sort O(V log V)
val topCandidates = Array(effK) { i -> indexed[i] }  // Lấy top 25
```

**Hậu quả nếu không sửa:**
- Hàm này được gọi **17 lần mỗi frame** (1 cho text EOS + 16 audio channels)
- Mỗi câu trung bình ~50 frames → 850 full sorts mỗi câu
- 1024 `IndexedLogit` object allocations × 850 = ~870K object allocations/câu → GC thrashing
- Sort O(1024 × log 1024) thay vì chỉ cần partial select O(1024)

**Cách sửa:**
1. Dùng **partial selection** (QuickSelect) hoặc min-heap thay vì full sort
2. Tái sử dụng mảng `indexed` thay vì allocate mới mỗi lần
3. Dùng `IntArray` + `FloatArray` thay vì `Array<IndexedLogit>` (tránh boxing)

## 🟡 Warnings (Nên sửa — Cải thiện hiệu năng đáng kể)

### 🟡 W1. EOS Check dùng brute-force O(textVocabSize × H) dot product

**File:** [`VieNeuOnnxEngine.kt`](file:///c:/Users/Administrator/Downloads/DocTruyenApk-main/app/src/main/java/com/skul9x/doctruyen/tts/vieneu/VieNeuOnnxEngine.kt#L298-L312)

**Triệu chứng:** Mỗi acoustic frame, kiểm tra EOS bằng cách tính dot product của `slot0` với **tất cả** 419 text embeddings:

```kotlin
for (v in 0 until textVocabSize) {      // 419 iterations
    val emb = textEmbeddings[v]
    var dot = 0f
    for (h in 0 until H) {              // 768 multiplications
        dot += slot0[h] * emb[h]
    }
}
```

**Hậu quả:** 419 × 768 = ~321K phép nhân mỗi frame × ~50 frames/câu = ~16M phép nhân thừa.

**Cách sửa:** Chỉ cần tính dot product cho **1 token duy nhất** là `speechGenerationEndTokenId` (ID=6), không cần tìm argmax toàn bộ vocab.

### 🟡 W2. `sampleCode` tính dot product lặp lại cùng pattern

**File:** [`VieNeuOnnxEngine.kt`](file:///c:/Users/Administrator/Downloads/DocTruyenApk-main/app/src/main/java/com/skul9x/doctruyen/tts/vieneu/VieNeuOnnxEngine.kt#L331-L338)

**Triệu chứng:** Hàm `sampleCode` tính logits = vec @ audioEmbeddings[ch].T bằng vòng for lồng nhau:

```kotlin
for (v in 0 until audioVocabSize) {   // 1024
    val emb = audioEmbeddings[ch][v]
    for (h in 0 until H) {            // 768
        dot += vec[h] * emb[h]
    }
}
```

Tổng: 1024 × 768 = ~786K phép nhân × 16 channels × ~50 frames = **~628M phép nhân/câu**.

**Cách sửa:** Chuyển sang dùng BLAS/SIMD (matrix multiply) qua ONNX Runtime hoặc pre-compute embedding matrix thành dạng liên tục trong memory để tận dụng CPU cache locality tốt hơn.

### 🟡 W3. AudioPlayer không tái sử dụng AudioTrack khi pause/resume

**File:** [`AudioPlayer.kt`](file:///c:/Users/Administrator/Downloads/DocTruyenApk-main/app/src/main/java/com/skul9x/doctruyen/tts/vieneu/AudioPlayer.kt#L42-L46)

**Triệu chứng:** `init()` kiểm tra `if (audioTrack != null) return` — OK. Nhưng `stop()` gọi `flush()` mà không release. Khi pipeline restart (seek, resume sau stop), `init()` thấy audioTrack != null → **không tạo lại** → có thể dùng track ở trạng thái inconsistent.

**Cách sửa:** Thêm `release()` trước khi re-init, hoặc dùng pattern lazy initialization đúng cách.

## Ưu điểm nổi bật (Những gì đã làm rất tốt ✅)

1. **Pre-warmed chunk cache** — Thiết kế thông minh, giảm TTFT xuống gần 0ms
2. **Atomic chunk silence** — Ghép PCM + silence thành 1 buffer duy nhất, loại bỏ false underrun
3. **Audio Focus handling** — Xử lý transient loss/duck đúng chuẩn Android
4. **Coroutine cancellation** — NonCancellable cho ONNX inference, proper cancellation handling
5. **Adaptive pre-buffering** — Dynamic threshold dựa trên chunk count & duration
6. **Smart Text Segmenter** — Protected abbreviations, dialogue detection, sub-clause splitting rất tốt
