## 5. DETAILED FINDINGS (CHI TIẾT BỆNH ÁN)

### [AUD-001] Vòng lặp suy luận AI không thể ngắt khi Stop / Đổi truyện gây nghẽn luồng và đóng băng âm thanh 3s–7.5s

- **Severity:** 🔴 Critical
- **Confidence:** High
- **Category:** Performance / Concurrency / Reliability
- **Status:** OPEN
- **Location:** `app/src/main/java/com/skul9x/doctruyen/tts/vieneu/TTSAudioPipeline.kt:492-495`, `TTSAudioPipeline.kt:376-394`, và `VieNeuOnnxEngine.kt:80-90`
- **Evidence:**
```kotlin
// TTSAudioPipeline.kt:492
val inferResult = withContext(NonCancellable) {
    val effectiveTemp = if (voiceName == "Thiền Tâm Đức") 0.25f else temperature
    engine.inferWithTiming(phonemes = phonemes, voiceName = voiceName, temperature = effectiveTemp)
}

// TTSAudioPipeline.kt:376
private fun stopInternal(resetIndex: Boolean) {
    pauseGate.resume()
    synthesisJob?.cancel()
    playbackJob?.cancel()
    ... // Không hề gọi engine.requestCancel()!
}
```

#### 🔎 Triệu chứng (Symptom)
Khi người dùng đang nghe đọc truyện mà bấm **Dừng (Stop)**, **Tua đoạn (Seek)**, hoặc **Chọn một truyện khác để đọc ngay**, ứng dụng bị đơ phản hồi âm thanh từ **3.0 đến 7.5 giây**. CPU vẫn bị chiếm dụng 94–100% trên các nhân hiệu năng cao, máy bị nóng lên dù người dùng đã bấm dừng.

#### 🧠 Nguyên nhân gốc (Root Cause)
1. `engine.inferWithTiming` trong vòng lặp tổng hợp thông thường bị bao bọc trong `withContext(NonCancellable)`. Lệnh hủy `synthesisJob?.cancel()` hoàn toàn bất lực và không thể làm gián đoạn coroutine đang chạy suy luận.
2. Hàm `stopInternal()` chỉ hủy job của coroutine mà **không gọi `engine.requestCancel()`**.
3. Cờ `cancelRequested` của `VieNeuOnnxEngine` chỉ được bật trong hàm `close()`, và engine **không có hàm `resetCancel()`** để khôi phục lại trạng thái bình thường.
4. Vì chunk cũ bị bỏ rơi vẫn tiếp tục chạy suy luận 600 frames trên CPU và chiếm giữ `engine.lock`, khi lệnh phát mới được gọi (`startPipeline()`), chunk mới cố gắng gọi `inferWithTiming` và bị block cứng ở `lock.withLock` cho đến khi chunk cũ bị hủy chạy xong toàn bộ!

#### ⚠️ Kịch bản Khai thác / Sự cố (Failure Scenario)
1. Người dùng mở Chương 1, TTS bắt đầu đọc câu dài (~120 ký tự, thời gian suy luận ~7.5s).
2. Sau 1 giây, người dùng nhận ra mở nhầm chương, bấm Stop và mở ngay Chương 2.
3. Người dùng thấy giao diện hiển thị "Đang phát...", nhưng không có bất kỳ âm thanh nào phát ra trong suốt 6.5s tiếp theo vì engine đang bận cày nốt Chương 1 trong vô vọng.
4. Người dùng bấm Play/Pause liên tục tưởng app bị treo, dẫn đến xung đột luồng và giật lag nghiêm trọng.

#### 💥 Hậu quả thực tế (Real-world Impact)
Phá hủy hoàn toàn trải nghiệm chuyển bài/đổi truyện. Gây lãng phí năng lượng pin khổng lồ (chạy AI vô ích) và làm điện thoại nóng ran.

#### 💊 Phác đồ điều trị (Recommended Fix)
1. Bỏ `withContext(NonCancellable)` khỏi vòng lặp phát thông thường trong `TTSAudioPipeline.kt`.
2. Bổ sung `fun resetCancel()` trong `VieNeuOnnxEngine.kt`.
3. Trong `TTSAudioPipeline.stopInternal()`, kích hoạt `engine.requestCancel()` để vòng lặp 15-channel giải phóng lock ngay lập tức trong vòng < 10ms.
4. Khi `startPipeline()` bắt đầu, gọi `engine.resetCancel()` để đón nhận phiên đọc mới.

```kotlin
// VieNeuOnnxEngine.kt
fun resetCancel() {
    cancelRequested = false
}

// TTSAudioPipeline.kt
private fun stopInternal(resetIndex: Boolean) {
    pauseGate.resume()
    engine.requestCancel() // Dừng ngay tức khắc vòng lặp ONNX native
    synthesisJob?.cancel()
    playbackJob?.cancel()
    ...
}

private fun startPipeline(startIndex: Int, storyId: Int = 0) {
    engine.resetCancel() // Sẵn sàng cho lượt suy luận mới
    ...
}
```

#### 🧪 Kiểm chứng (Verification)
Viết test đo thời gian từ lúc gọi `stop()` khi đang suy luận dở đến khi `inferWithTiming` ném `InterruptedException` và nhả `lock` — thời gian phải < 50ms thay vì 7500ms.

### [AUD-002] Nhận diện sai định dạng lượng tử hóa khiến model FP32 bị ép chạy cấu hình bộ đệm INT8, gây giật lag và vấp âm thanh

- **Severity:** 🟠 High
- **Confidence:** High
- **Category:** Correctness / Performance
- **Status:** OPEN
- **Location:** `app/src/main/java/com/skul9x/doctruyen/tts/vieneu/OnnxSessionManager.kt:131-136`
- **Evidence:**
```kotlin
// OnnxSessionManager.kt:131
val sharedData = File(parent, "vieneu_backbone_shared.data")
if (sharedData.exists()) {
    return QuantizationType.INT8
}
```

#### 🔎 Triệu chứng (Symptom)
Khi cấu hình chọn độ chính xác **FP32** (chất lượng cao) trong Cài Đặt hoặc chạy bộ mô hình trong thư mục `backbone/`, hệ thống vẫn nhận diện nhầm là `INT8`. Gây vấp đĩa, khựng âm liên tục (Audio Starvation Underrun) do bộ đệm quá ngắn. Đồng thời làm rớt hàng loạt unit tests liên quan đến Precision Switching.

#### 🧠 Nguyên nhân gốc (Root Cause)
File `vieneu_backbone_shared.data` là định dạng lưu trữ trọng số ngoài chuẩn của ONNX (khi model lớn >2GB hoặc tách weights). File này tồn tại ở cả thư mục FP32 (`src/main/assets/vieneu/backbone/vieneu_backbone_shared.data` nặng 103MB) lẫn thư mục INT8. Logic kiểm tra `if (sharedData.exists()) return QuantizationType.INT8` biến tất cả các model FP32 thành INT8.

#### ⚠️ Kịch bản Sự cố (Failure Scenario)
Mô hình FP32 trên CPU di động có RTF ~1.8x - 2.5x (chậm gấp 2-3 lần so với INT8). Để phát mượt mà, FP32 bắt buộc phải pre-buffer tối thiểu **7,500ms (7.5 giây)**. Do bị nhận diện nhầm là INT8, hệ thống chỉ pre-buffer **2,000ms**, khiến bộ đệm bị phát cạn kiệt chỉ sau vài giây đầu tiên, gây ra tình trạng đọc 1 câu lại ngắt 2-3 giây để chờ CPU.

#### 💥 Hậu quả thực tế (Real-world Impact)
Người dùng muốn nghe giọng đọc chuẩn FP32 chất lượng cao sẽ gặp hiện tượng nói lắp, giật cục, biến dạng âm thanh không thể nghe nổi.

#### 💊 Phác đồ điều trị (Recommended Fix)
Xóa bỏ heuristic sai lầm kiểm tra `sharedData.exists()`. Chỉ xác định INT8 dựa vào:
1. Tên thư mục chứa (`parent.name == "backbone_int8"` hoặc đường dẫn chứa `int8`).
2. Quét sâu bytecode của model tìm các toán tử lượng tử hóa thực sự (`MatMulInteger`, `DynamicQuantizeLinear`, `QLinearMatMul`).

```kotlin
// Sửa trong OnnxSessionManager.kt:
val parent = file.parentFile
if (parent != null && parent.exists() && parent.name.contains("backbone_int8")) {
    return QuantizationType.INT8
}
```

#### 🧪 Kiểm chứng (Verification)
Chạy lại `DynamicPrecisionSwitchingTest.testOnnxSessionManager_precisionSwitchingAndResolution` — phải PASS 100% với `sessionFp32.quantizationType == FP32`.

### [AUD-003] Cấp phát lặp 9,000 JNI Tensor vô nghĩa trong vòng lặp sinh âm thanh gây nghẽn rác bộ nhớ Native

- **Severity:** 🟡 Medium
- **Confidence:** High
- **Category:** Performance / Resource Efficiency
- **Status:** OPEN
- **Location:** `app/src/main/java/com/skul9x/doctruyen/tts/vieneu/VieNeuOnnxEngine.kt:628-644`
- **Evidence:**
```kotlin
for (ch in 1 until config.nVq) {
    ...
    val posTensor = OnnxTensor.createTensor(env, LongBuffer.wrap(longArrayOf((ch + 1).toLong())), longArrayOf(1, 1))
    feed["position_ids"] = posTensor
    ...
    posTensor.close()
}
```

#### 🔎 Triệu chứng (Symptom)
Tốc độ suy luận RTF tiệm cận 1.0x (chạy mất 70.8s cho đoạn audio 75.2s), CPU luôn trong trạng thái quá tải và sinh nhiệt cao.

#### 🧠 Nguyên nhân gốc (Root Cause)
Trong hàm `acousticFrame()`, với mỗi kênh $ch \in [1..15]$ qua 600 khung hình của 1 chunk, đối tượng `posTensor` được tạo mới và đóng lại 15 lần/frame với giá trị tĩnh không đổi `ch + 1` ($2, 3, \dots, 16$). Tổng cộng có tới **9,000 lần gọi JNI cấp phát và giải phóng OnnxTensor** cho mỗi câu văn đơn lẻ!

#### 💥 Hậu quả thực tế (Real-world Impact)
Gây áp lực lớn lên bộ cấp phát bộ nhớ native của Android C++ Runtime, tiêu tốn chu kỳ CPU cho các thao tác JNI bridge không cần thiết.

#### 💊 Phác đồ điều trị (Recommended Fix)
Khởi tạo mảng tensor vị trí tĩnh 1 lần duy nhất trong `VieNeuOnnxEngine` (`cachedChannelPosTensors = Array(16) { ... }`) và tái sử dụng xuyên suốt toàn bộ các frames/chunks. Giải phóng trong `performResourceTeardown()`.

### [AUD-004] Rò rỉ Activity Context trong Foreground Service dài hạn qua Callback tiến trình

- **Severity:** 🟡 Medium
- **Confidence:** High
- **Category:** Reliability / Memory Leak
- **Status:** OPEN
- **Location:** `app/src/main/java/com/skul9x/doctruyen/StoryDetailActivity.kt:120-128`, `ReadingService.kt:423-430`
- **Evidence:**
```kotlin
// StoryDetailActivity.kt:121
val progressBar = findViewById<LinearProgressIndicator>(R.id.progressTts)
boundService.setProgressCallback { progress ->
    runOnUiThread {
        if (!isFinishing && !isDestroyed) {
            progressBar.progress = progress
        }
    }
}
```

#### 🔎 Triệu chứng (Symptom)
Sau khi người dùng mở xem nhiều truyện khác nhau rồi quay lại màn hình chính, dung lượng RAM của ứng dụng tăng dần đều không giảm. Có nguy cơ crash `OutOfMemoryError` sau vài giờ nghe truyện.

#### 🧠 Nguyên nhân gốc (Root Cause)
Lambda truyền vào `setProgressCallback` ngầm giữ tham chiếu mạnh (strong reference) tới `StoryDetailActivity` và cây View `progressBar`. `ReadingService` là một Foreground Service sống độc lập và lâu dài. Nếu `StoryDetailActivity` bị destroy mà Service chưa bị giải phóng, callback này giữ chặt Activity cũ trong RAM.

#### 💊 Phác đồ điều trị (Recommended Fix)
Đảm bảo hàm `onDestroy()` của `StoryDetailActivity` luôn chủ động gọi `readingService?.removeStateCallback()` (hàm này đã có sẵn logic gán `progressCallback = null`), đồng thời sử dụng `WeakReference` đối với listener UI trong `ReadingService`.

### [AUD-006] Lỗi phân tích mảng Scalar 0-D trong NpzReader làm mất thông số chuẩn hóa âm thanh

- **Severity:** 🔵 Low
- **Confidence:** High
- **Category:** Correctness / Reliability
- **Status:** OPEN
- **Location:** `app/src/main/java/com/skul9x/doctruyen/tts/vieneu/NpzReader.kt:168-176`
- **Evidence:**
```kotlin
val shape = parseShape(headerStr)
var totalElements = if (shape.isEmpty()) 0 else 1
for (dim in shape) {
    totalElements *= dim
}
val floatData = FloatArray(totalElements)
if (totalElements == 0) {
    return NpyArray(shape, floatData)
}
```

#### 🔎 Triệu chứng (Symptom)
Hàm `reader.getScalarFloat("xvec_ln_eps")` luôn trả về `null`, làm fail test `NpzReaderTest.testReadHeadsNpz`.

#### 🧠 Nguyên nhân gốc (Root Cause)
Trong NumPy, mảng scalar có shape rỗng `()` (`shape.isEmpty() == true`), nhưng số lượng phần tử thực tế là **1**, không phải 0. Đoạn code gán `totalElements = 0` dẫn đến việc bỏ qua không đọc 4 bytes của scalar từ `ZipInputStream`, khiến stream bị lệch offset cho các phần tử phía sau.

#### 💊 Phác đồ điều trị (Recommended Fix)
Khởi tạo `var totalElements = 1` bất kể shape rỗng hay có chiều:
```kotlin
var totalElements = 1
for (dim in shape) {
    totalElements *= dim
}
```
